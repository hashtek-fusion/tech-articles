01

Why staged, not "big bang"

Enterprise repos already carry review gates, CI, and institutional knowledge that live in people's heads, not in the code. An agent dropped in without that context will write code that compiles and still gets rejected — wrong logging convention, wrong exception pattern, wrong test double. The fix isn't a smarter model; it's an onboarding sequence, the same one you'd use for a new engineer, compressed into files an agent reads before it writes.

The model that works in practice is a trust ladder: read-only exploration → suggested diffs a human applies → agent-opened PRs on a narrow task class → broader autonomy with spend and merge gates. Every phase below maps to a rung on that ladder, and every rung is earned by evidence (PR acceptance rate, defect rate, cost per merged PR), not by calendar time.

Starting task class Constrain the pilot to two categories only: well-reproduced bug fixes (a failing test or clear repro exists) and small, additive features (new endpoint, new field, new component) with an existing pattern to copy. Both have a cheap, objective "did it work" signal — a test passes, a build succeeds — which is exactly what makes them safe to automate first.
02

Pre-flight repo checklist

None of this is agent-specific — it's the baseline that makes autonomous PRs from anyone, human or agent, safe to merge. If any of these are missing, fix them before onboarding an agent, not after.

Branch protection on default branchNo direct pushes; required status checks; required review count ≥ 1 for agent-authored PRs even if humans can self-merge elsewhere.
CI actually gates mergeLint, type-check, unit tests, and (ideally) an integration smoke test all run and block merge on failure — this is the agent's primary feedback loop.
Meaningful test coverage on the pilot areaAn agent fixing a bug without a regression test to anchor to will "fix" the symptom, not the cause. Backfill tests in the pilot module first if needed.
Secrets are out of the repo and out of reachNo secrets in env files an agent might read; secret scanning enabled; agent's GitHub token/PAT scoped to the pilot repo only, not org-wide.
CODEOWNERS on the pilot pathsEnsures agent PRs route to a reviewer who actually knows the module, not whoever is next in a round-robin.
A place for the agent-context file to liveConfirm nothing already claims CLAUDE.md/AGENTS.md at repo root for an unrelated purpose.
03

The rollout: seven phases

Each phase produces a concrete artifact in the repo. None of it is theoretical — by the end of Phase 3 an agent working cold on the repo should read almost the way a well-onboarded contractor would.

0
Scope the pilot

Pick one repo, one task class, one owner

Choose a repo with decent tests and a low-blast-radius module — not the billing engine. Name a single engineer as the rollout owner who reviews every agent PR for the first two weeks. Write down the task class explicitly (e.g. "bugs with a linked failing test in the orders-api module") so scope creep is visible when it happens.

Exit gate → written scope + owner assigned
1
Repo context file

Write the CLAUDE.md / AGENTS.md

This is the single highest-leverage artifact in the whole rollout. It's a markdown file at repo root that every agent reads before touching code: what the service does, the architecture in five sentences, the coding style the team actually enforces (not the aspirational one), the exact commands to build/test/lint, and an explicit do/don't list. Treat it like onboarding docs for a new hire — because that's what it is.

CLAUDE.md — excerpt 
# Orders API

Spring Boot 3 service owning order lifecycle. Talks to `inventory-svc` via gRPC,
publishes `OrderPlaced`/`OrderCancelled` events to Kafka.

## Build & test
- `./gradlew build` — full build, must pass before any PR
- `./gradlew test --tests "*OrderServiceTest"` — fast loop for order logic
- Never run `./gradlew publish` — that's a release step, human-only

## Conventions
- Controllers stay thin: validation + delegate to a `*Service`, no business logic
- All service methods that touch money return `Result<T, OrderError>`, never throw
  for expected failure paths (see `OrderError.java`)
- New endpoints: copy the pattern in `CancelOrderController`, not `LegacyRefundController`
  (the latter is deprecated, do not imitate it)

## Do not
- Do not modify anything under `src/main/java/.../legacy/` — frozen, migration in flight
- Do not add new Kafka topics without a human decision (infra cost + ownership)
Exit gate → agent's first three suggested diffs match team style without correction
2
Skills

Encode institutional patterns as reusable skills

CLAUDE.md tells the agent about the repo; skills tell it how your team does a recurring kind of task, in enough detail to reuse without re-deriving it each time. A skill is a short instruction file (plus optional scripts/templates) triggered by task type: "add a REST endpoint," "add a DB migration," "write a component with our design system." This is where design patterns and code-review norms actually stick, because the agent reads the playbook instead of pattern-matching on whatever code happens to be nearby.

.claude/skills/add-rest-endpoint/SKILL.md — excerpt 
---
name: add-rest-endpoint
description: Use when adding a new REST endpoint to a Spring controller in this repo
---
1. Add the method to the relevant `*Controller`, thin — delegate to `*Service`
2. Validate input with a `@Valid` request DTO in `dto/request/`, never raw Map
3. Service layer returns `Result<T, DomainError>`; map errors to HTTP status in
   the controller's `@ExceptionHandler`, matching the table in `ERROR_MAPPING.md`
4. Add an OpenAPI annotation matching existing endpoints in the same controller
5. Write a `@WebMvcTest` for the endpoint before opening a PR — CI will reject
   endpoint PRs with no test targeting the new path
Exit gate → 2–3 skills covering the pilot task class's most common shapes
3
Plugins & connectors

Give the agent the same tools a human contributor has

A human fixing a bug checks the ticket, greps internal docs, and maybe pings someone on Slack. An MCP connector or plugin gives the agent the equivalent: read access to the issue tracker (Jira/Linear) so it can pull the actual bug report, a docs connector for internal architecture pages, and a package-registry connector if internal packages aren't on public npm/PyPI/Maven. Scope every connector to read-only where the agent doesn't need to write, and to the specific project/space where it does.

Exit gate → agent can resolve a ticket reference to full context without being pasted the ticket manually
4
Hooks

Turn tribal safety rules into enforced ones

Hooks run deterministic checks around agent actions — before a commit, before a push, before a tool call completes. They convert "please remember to..." into something that actually blocks. Three worth having from day one: a pre-commit hook that runs lint + fast tests before any commit is created, a pre-push hook that refuses a push if the target is a protected branch, and a PR-open hook that enforces the PR template (linked issue, test evidence, a "generated by agent" label).

.claude/hooks — conceptual 
PreToolUse(Bash: git push)  → reject if branch in [main, release/*]
PostToolUse(Edit/Write)     → run linter on changed files, surface failures inline
PreToolUse(git commit)      → block if fast test suite fails
Exit gate → at least one real incident where a hook caught something a human would have caught in review, before review
5
Human-in-the-loop gates

Decide, in writing, what a human must approve

Not every decision needs a human, but some always do. Write the list down rather than relying on judgment call each time: merge approval always human; anything touching auth, payments, data deletion, or schema migrations always human, regardless of size; any PR the agent flags as low-confidence routes to a human before CI even runs, to avoid burning cycles on a doomed approach.

Exit gate → escalation list reviewed by eng lead + security, not just the rollout owner
6
Expand scope

Widen the task class only when metrics say so

Move from bug fixes to small features, then from one repo to a second, then relax review intensity — each step gated on the same numbers: PR acceptance rate without major rework, defect escape rate post-merge, and cost per merged PR holding flat or falling. If any metric regresses when scope widens, roll the scope back one notch before debugging why, then widen again once fixed.

Exit gate → two consecutive weeks of stable metrics at the new scope
04

Stack-specific onboarding

The phases above are stack-agnostic; the content inside CLAUDE.md and your skills isn't. Three starting points below — swap in your team's real conventions, these are illustrative shapes, not templates to copy verbatim.

CLAUDE.md should state: the Spring profile structure (dev/test/prod), whether the team uses constructor injection exclusively (say so — agents default to field injection otherwise), the exception-handling convention (checked vs. unchecked, `Result`-style wrappers vs. exceptions), and the test stack (JUnit 5 + Mockito vs. Testcontainers for integration).

High-value skills: "add a JPA entity + repository + migration," "add a REST endpoint" (as above), "add a scheduled/async job following our `@Async` + retry pattern."

Common correction needed early: agents default to `@Autowired` field injection and generic `RuntimeException` — call both out explicitly as "don't" items if the team avoids them.

CLAUDE.md should state: module system (ESM vs CommonJS), the state-management or data-fetching convention on the frontend, whether the backend uses a framework's DI or plain function composition, and the exact test runner + how mocks are structured (this varies wildly team to team).

High-value skills: "add an API route + Zod/validation schema + test," "add a React component matching our design system" (point at a real reference component, not a description), "add a DB migration with our ORM."

Common correction needed early: agents mix `any` back in under type pressure, and default to whatever data-fetching pattern is most common in public training data rather than the team's actual one (e.g. React Query vs. hand-rolled hooks) — pin this explicitly.

CLAUDE.md should state: dependency manager in use (poetry/uv/pip-tools), whether the codebase is typed (mypy/pyright strict or not) and how strictly enforced, the web framework's error-handling convention, and async vs. sync boundaries if the codebase mixes both.

High-value skills: "add an endpoint + pydantic schema + test," "add a Celery/background task following our retry/idempotency pattern," "add a DB migration with Alembic."

Common correction needed early: agents silently drop type hints under refactor pressure, and reach for `except Exception` broadly unless the team's narrower exception convention is written down.

06

Enterprise skills & plugins registry

Once two or three teams have each built their own "add a REST endpoint" skill, the per-repo model in Phases 1-4 starts duplicating work and drifting into inconsistent agent behavior across LOBs. The fix: a single central Git repo of skills/plugins, owned by an AI Enablement team, that any domain repo can pull from and any team can contribute to.

central-agent-registry/ — layout
central-agent-registry/ ├── shared/skills/ # cross-domain: PR hygiene, test-writing, commit style ├── domains/ │ ├── payments/skills/ # LOB-specific: reconciliation, ledger patterns │ ├── claims/skills/ │ └── platform/skills/ ├── plugins/ # bundled skill+hook+MCP-connector packages ├── REGISTRY.md # index: name → domain → owner → version └── CODEOWNERS # AI Enablement owns root; domain leads own their folder
Why central One reviewed, versioned "add a REST endpoint" skill instead of five slightly-different ones. Security/quality review happens once, centrally — not once per team, per repo.

Contribution flow — a team publishes a skill

flowchart LR
    A[Domain team finds\na reusable pattern] --> B[Author skill/plugin\nin a feature branch]
    B --> C[Open PR to\ncentral registry]
    C --> D{AI Enablement\nreview}
    D -- changes requested --> B
    D -- approved --> E[Merge to main]
    E --> F[Tag semver release]
    F --> G[Publish to\nREGISTRY.md index]

Consumption flow — a team's repo uses it

flowchart LR
    A[Team repo pins registry\nversion in manifest] --> B[Agent session starts\nin team's repo]
    B --> C[Skill/plugin pulled\nfrom central registry]
    C --> D[Agent applies skill\nduring the task]
    D --> E[Usage signal logged\n- optional telemetry]
    E --> F[AI Enablement sees\nadoption metrics]
AI Enablement
Owns the repo, reviews every PR for quality/security/naming, cuts versioned releases, deprecates stale skills.
Domain / LOB teams
Consume shared + their own domain skills; contribute new ones back via PR when they build something reusable.
Security & Compliance
Spot-reviews sensitive categories (data access, payments, PII-handling skills) before release.
  • Versioning: semver tags on the registry; consuming repos pin a version, not main — no surprise behavior change mid-sprint.
  • Consumption mechanism: git submodule, package manifest reference, or a plugin-marketplace entry pinned to a tag — whichever your agent tooling supports for installing plugins at session start.
  • Deprecation: mark a skill deprecated in REGISTRY.md with a replacement pointer; give consumers one release cycle before removal.
07

Human-in-the-loop & governance

The goal isn't to slow the agent down everywhere — it's to make sure the handful of decisions that matter always cross a human, while everything else flows.

  • Label everything agent-authored. A PR label (agent-authored) plus a footer noting the model/tool used — makes audit trivial later and lets reviewers calibrate scrutiny.
  • Merge is always a human action. Even at high trust levels, the merge button is a person's, not the agent's — auto-merge-on-green is a policy choice to make explicitly, not a default to fall into.
  • Named review owner per pilot, not a queue. Diffuse review responsibility is how low-quality agent PRs slip through — someone specific is accountable for the first weeks.
  • Escalation path for uncertainty. The agent should have an explicit "I'm not confident, flagging for human input" path rather than guessing past a threshold — reward this behavior, don't penalize it as a failure to complete the task.
  • Audit trail. Keep the agent's plan/reasoning artifact (session log, PR description) attached to the PR — when something goes wrong six weeks later, "what did it think it was doing" needs an answer.
08

Token usage & cost control

Cost discipline is a design constraint from day one, not a dashboard you check after the bill arrives.

Set a per-task budget, not just a monthly capA single runaway task (agent loops on a failing test, keeps retrying) should hit a hard stop — token or turn count — well before it becomes a monthly-bill problem.
Tier models to the taskUse a smaller/cheaper model for triage — "is this bug report reproducible, what file is it likely in" — and reserve the strongest model for the actual fix generation and verification.
Keep CLAUDE.md and skills leanEvery session reloads this context; a bloated file is a recurring tax on every task. Prompt caching helps with repeat cost, but the leanest fix is not writing padding into the file in the first place.
Bound tool-call loopsCap retries on a failing test or lint fix — after N attempts, escalate to a human instead of continuing to spend on the same wall.
Track cost per merged PR, not just cost per runA cheap run that never produces a mergeable PR is a worse ratio than an expensive run that does. Watch the ratio, not either number alone.
Alert on spend anomaliesA spend spike is often the first visible symptom of a looping agent or a runaway task — wire an alert before it's a line item someone asks about a month later.
09

Rollout maturity ladder

A shared scorecard for where a given repo actually sits — useful for a status update to engineering leadership without re-litigating the whole plan each time.

L0

No agents

Manual development only. No context files, no pilot scoped.

L1

Read-only / suggestion

CLAUDE.md exists; agent suggests diffs a human applies manually. No agent-opened PRs yet.

L2

Narrow autonomous PRs

Agent opens PRs for the pilot task class only (reproduced bugs, small additive features); every PR human-reviewed and human-merged; hooks enforce lint/test/branch rules.

L3

Broader task class, metrics-gated

Small features beyond the pilot module; skills cover most common shapes; cost-per-merged-PR tracked and stable; escalation path exercised, not just documented.

L4

Multi-repo, standing practice

Pattern replicated across repos with repo-specific CLAUDE.md/skills; governance policy (labels, merge rules, spend alerts) is org-standard, not pilot-specific.

10

Common pitfalls

Scope

Widening the task class too fast

One good week of bug-fix PRs isn't evidence the agent is ready for open-ended feature work — gate on the metrics in Phase 6, not enthusiasm.

Guardrails

Treating tests as optional context

An agent without a failing test to anchor to will "fix" whatever it guesses is wrong. No repro, no test, no autonomous PR.

Security

Overscoped credentials

An org-wide PAT or write access to unrelated repos turns a contained pilot into an org-wide blast radius if anything goes sideways.

Cost

No loop or retry ceiling

A stuck agent retrying the same failing approach is the single most common source of surprise spend — cap it structurally, not by watching a dashboard.

Process

No rollback plan

Know in advance how to pause the pilot (revoke the token, disable the workflow) without a scramble — write it down before you need it, not during an incident.

Context

Stale CLAUDE.md

A context file that isn't updated when conventions change becomes actively misleading — assign it an owner the same way you'd own a README.
