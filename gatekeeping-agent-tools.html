Gatekeeping Agent Tools

How to expose an existing Lambda function as a tool an AI agent can call through Amazon Bedrock AgentCore Gateway — and why that alone doesn't control which tools a given caller may use. This is a generic walkthrough of the wiring, the gap it leaves, and how AgentCore's Policy service (Cedar-based, evaluated per tool call) closes it.

01 · The shape of a Gateway integration

AgentCore Gateway sits between an agent (or any MCP client) and the backend that does the real work. In the simplest, most common setup, that backend is a Lambda function the Gateway invokes directly — no OpenAPI spec to author or host, just an inline description of the tool's name, purpose, and input shape.

Two decisions here are independent of each other, and worth naming separately because it's easy to conflate them:

  • Target type — how the Gateway reaches the backend. A native Lambda target (shown above) invokes directly with the Gateway's own credentials. An OpenAPI-schema target instead proxies to an HTTP API, with its own separate credential provider. Neither implies anything about who's allowed to call the Gateway.
  • Authorizer type — how the Gateway authenticates callers. AWS_IAM means only SigV4-signing callers in your account get in. CUSTOM_JWT validates an OAuth bearer token against any OIDC-compatible identity provider, which is what lets a caller outside AWS — a third-party agent platform, a laptop running an MCP client — connect at all.

02 · Exposing a Lambda as a tool

Given a Lambda that already does something useful, turning it into a tool an agent can call is mostly declarative. In order:

  1. Create the Gateway.

    AWS::BedrockAgentCore::Gateway, ProtocolType: MCP, and an AuthorizerType — start with AWS_IAM if every caller is inside your own account, or CUSTOM_JWT with a DiscoveryUrl pointed at your identity provider if any caller isn't. This choice is one-way in practice: the live service rejects an in-place change to an existing gateway's AuthorizerType, so switching later means deleting and recreating it.

  2. Give the Gateway an execution role.

    Trusted by the bedrock-agentcore.amazonaws.com service principal, with a permission policy scoped to lambda:InvokeFunction on exactly the Lambda ARN you're exposing — not a wildcard.

  3. Add a GatewayTarget.

    AWS::BedrockAgentCore::GatewayTarget, native Lambda configuration, CredentialProviderType: GATEWAY_IAM_ROLE (so it uses the role from step 2, not a separate credential provider), and an inline ToolSchema — one entry per tool, each with a Name, a Description the agent will read to decide when to call it, and an InputSchema.

  4. Grant the Gateway permission on the Lambda side too.

    A resource-based AWS::Lambda::Permission allowing bedrock-agentcore.amazonaws.com to invoke it, with SourceArn scoped to this specific Gateway's ARN.

  5. Make sure the Lambda actually understands the call.

    This is the one step that isn't boilerplate. The Gateway invokes your Lambda with the tool's arguments as the event payload and expects a response it can hand back as the tool result. A Lambda that was only ever written to sit behind an API-Gateway-proxy integration won't necessarily understand that shape without an adapter — this is real integration work, not configuration.

  6. Test it as a real MCP client would.

    Bearer-token (CUSTOM_JWT) auth can be exercised with any generic MCP client, since it's just a header. SigV4 (AWS_IAM) can't — it needs a fresh signature computed over each request, so a tool that only lets you paste a static header won't work for it; you need something that signs the request itself.

Once a Gateway and its Auth setup exist, adding a second Lambda as another tool is cheaper still: authorization is configured once, at the Gateway, not per target — so a new GatewayTarget under the same Gateway inherits the existing auth automatically. What doesn't get cheaper is step 5 and the schema in step 3, and — as the next section covers — nothing here yet decides whether a given caller should be allowed to use that new tool.

03 · The gap: authenticated, not authorized

The load-bearing sentence

The Gateway's authorizer answers one question — is this caller who they claim to be? — once, at the door. It does not answer which tools should this caller be allowed to use? A valid token or IAM identity unlocks every tool behind that Gateway equally. There's no schema field, no per-target setting, that narrows it further.

That's fine for a Gateway with one read-only tool. It stops being fine the moment a second tool does something with side effects, touches different data, or should only be available to some callers and not others — and by then, the tools are already sharing one door.

04 · Per-tool authorization with Policy

AgentCore's Policy service sits exactly at that gap. A policy engine holds a set of rules, written in Cedar (AWS's open-source authorization language — also authorable as plain English, which gets translated to Cedar and validated before it's saved). You associate the engine with a Gateway once, and from then on, every tool call is evaluated against those rules before the Lambda is ever invoked.

Three things worth knowing about how the engine sees a request:

  • The principal depends on how the Gateway authenticates. A CUSTOM_JWT Gateway gives Cedar an AgentCore::OAuthUser built from the token's sub claim, with every other JWT claim available as a tag (principal.hasTag("role"), principal.getTag("role")). An AWS_IAM Gateway gives an AgentCore::IamEntity whose id is the caller's IAM ARN.
  • The action is one per tool, named <targetName>___<toolName> — the same double-underscore-joined name a plain tools/list call already returns, so there's nothing new to look up.
  • The resource is the Gateway itself (AgentCore::Gateway::"<arn>"), and context.input exposes the tool call's actual arguments, so a rule can also gate on what is being asked for, not just who's asking.

Evaluation is default-deny (nothing is allowed unless a rule permits it) and forbid-wins (any matching forbid overrides every permit). And it isn't limited to gating tools/call — a caller's tools/list response only shows the tools they're actually authorized to use, so an unauthorized tool doesn't just fail quietly, it doesn't appear at all.

Rolling it out without a surprise outage

The Gateway's link to a policy engine carries a Mode: LOG_ONLY evaluates every rule and records the decision to CloudWatch without blocking anything, so you can watch what your rules would have done against real traffic before anything depends on it. Flip to ENFORCE once that log looks right.

05 · A worked two-tool example

Say a Gateway target exposes two tools: get_data (read-only, safe for anyone authenticated) and update_data (writes something, and should be restricted). Three Cedar rules cover this:

Rule 1Permit
permit(
  principal is AgentCore::OAuthUser,
  action == AgentCore::Action::"DataAPI___get_data",
  resource == AgentCore::Gateway::"arn:aws:bedrock-agentcore:us-west-2:111122223333:gateway/data-gw"
);

Any authenticated caller can read. No conditions needed — this is the baseline.

Rule 2Permit, conditional
permit(
  principal is AgentCore::OAuthUser,
  action == AgentCore::Action::"DataAPI___update_data",
  resource == AgentCore::Gateway::"arn:aws:bedrock-agentcore:us-west-2:111122223333:gateway/data-gw"
)
when {
  principal.hasTag("role") &&
  principal.getTag("role") == "editor" &&
  context.input has reason
};

Writing requires both an identity condition (the JWT's role claim must say editor) and an input condition (the call must include a reason field) — identity-based and parameter-based rules compose in the same policy.

Rule 3Forbid, wins regardless
forbid(
  principal is AgentCore::OAuthUser,
  action == AgentCore::Action::"DataAPI___update_data",
  resource == AgentCore::Gateway::"arn:aws:bedrock-agentcore:us-west-2:111122223333:gateway/data-gw"
)
when {
  principal.hasTag("client_id") &&
  principal.getTag("client_id") == "read-only-integration-client"
};

One specific client is blocked from writing outright — even if it somehow carried an editor role tag, forbid-wins means this rule overrides rule 2 for that one caller.

06 · Six things that will trip you up

An authorizer type change means delete-and-recreate

The CloudFormation schema lists a Gateway's AuthorizerType as an updatable property. The live service disagrees — an in-place switch is rejected at deploy time. Budget for removing the Gateway (and its targets/permissions) and recreating it fresh whenever this needs to change.

Target type and authorizer type are unrelated decisions

Whether the Gateway calls a Lambda directly or proxies to an OpenAPI backend has no bearing on who's allowed to call the Gateway in the first place. Don't reach for one to fix a problem in the other.

A non-Cognito IdP's client restriction can misbehave

With a generic OAuth provider issuing machine-to-machine (client_credentials) tokens, the Gateway's built-in AllowedClients field can produce a false "insufficient scope" rejection on an otherwise valid token — independent of anything in AllowedScopes. A CustomClaims rule matching an identity claim (like the token's azp) is a safer way to restrict which client can call in — or, once Policy is in the picture anyway, express the same restriction as a Cedar principal/tag condition and skip the built-in field entirely.

SigV4 can't be tested with a pasted header

A bearer token is a static string you can paste into any client. SigV4 is a signature computed fresh over the exact request being sent — method, path, timestamp, body hash. Any tool you use to exercise an AWS_IAM Gateway has to actually sign each request, not just forward a header you copied earlier.

Tool names in results aren't the names you wrote

A tool declared as get_data in the schema shows up from tools/list — and in Cedar's action — as <targetName>___get_data. Match on the qualified name, not the bare one, in both places.

No policy engine means no per-tool boundary at all

Without Policy attached, a Gateway's authorizer is a single door for every tool behind it. That's a reasonable starting point for one low-stakes tool. It stops being reasonable the moment a second tool has a meaningfully different risk profile — plan for Policy before that tool ships, not after.
